## A. Executive summary

This is a substantial React/TypeScript single-school prototype with a deterministic 1,000-student demo dataset, distinct Principal/Class Teacher/Subject Teacher views, a central permissions module, operational screens, and a Firestore repository. The Principal dashboard and teacher workspaces are useful starting points. The student dossier, marks, attendance, reports, notes, and CSV/XLSX utilities have real implementations.

The demo UI is active. Dashboard search opened the correct student dossier. The Principal saw marks read-only; the Subject Teacher saw only Science marks in the observed dossier and was denied whole-school attendance and the Principal-only comparison; the dual-responsibility Class 10-A teacher could access Mathematics work in other assigned classes.

Critical findings:

1. **Cross-section individual attendance disclosure:** the Class 10-A/Mathematics dual teacher opened a Class 10-B student's individual attendance history by direct URL. Outside their own class, this teacher should see aggregate attendance only. The displayed 60-day history is also generated by a formula rather than session records, so its dated rows and XLSX export are not verified attendance. See src/pages/attendance/StudentAttendanceHistory.tsx and src/domain/permissions.ts.
2. **Marks finalization is inconsistent:** the page calls a save “finalized” and locks only its current React state, while both repositories persist status submitted; on reload the page locks only finalized. Demo mode therefore allows editing after refresh. Firebase rules instead block updates to submitted, so UI and providers diverge.
3. **Academic comparison is hard-coded:** five static subject rows compare only Class 10-A and 10-B, without assessment or section selection. The page still says “Cross-Cohort Academic Performance Comparison.”
4. **Firestore rules do not cover repository behavior:** studentFollowUps is not authorized and falls through to default deny; Subject Teachers cannot read incidents although the UI offers their notes; staff and subject assignments are readable by all authenticated staff. Storage rules include unsupported office/admin roles and unscoped class-teacher access.
5. **Student count mismatch:** directory says 1,000 of 1,000 enrolled students while its table state says “0–500 of 1001 items.”
6. **Subject Teacher dashboard defect:** visible text says “Science Teacher: undefined.”
7. Test suite: 39 passed, 1 timed out at 5 seconds. Lint: 0 errors, 20 warnings. Build succeeded, but the minified main JS chunk is about 737 kB.

Severity definitions: P0 serious security exposure or critical workflow blocked; P1 major role/data integrity/core workflow defect; P2 important usability or misleading output; P3 smaller polish/accessibility issue.

## B. Product understanding

HanuJai is intended as a private, single-school ERP pilot for roughly 1,000 students in Classes 1–10, sections A/B. The three profiles are Principal, Class Teacher, and Subject Teacher. Core workflows are student lookup, attendance, assessment marks, academic progress, and relevant teacher notes/follow-up.

The Principal has school-wide read-only oversight. A Class Teacher has responsibility for their assigned class. A Subject Teacher has assigned subject/class work and aggregate attendance. A dual-role user keeps one identity with separate class and subject assignments. These tasks should stay simple.

The actual board, attendance schedule, grading rules, and thresholds were not provided and remain **unverified**. The app's CBSE, 75%, marking-hour and pass-mark claims must not be treated as approved school policy.

## J. Firebase and authorization

### Firestore
- Default rule denies unmatched access.
- staff, classes, subjects, subjectAssignments, assessments are readable by all authenticated staff. Staff/assignment access should be minimized.
- Student reads allow Principal, assigned CT by assignedClassId, or subject teacher for any assignedClasses class; subject users can read whole student documents in assigned classes.
- Attendance sessions allow Principal and assigned CT read/write; there is no aggregate-only Subject Teacher path.
- Corrections: Principal read, CT create, updates/deletes denied.
- Marks: rule blocks existing submitted, not finalized. UI/providers call finalization but persist submitted.
- Incidents: Principal/CT read; Subject Teacher create but not read. Subject Notes likely fails in Firebase mode.
- studentFollowUps has no rule and is default-denied. Firestore repository checks only Principal role before write, not assignment.
- Audit event writes require actorId to match auth UID; coverage across mutations was not proved.

### Storage
storage.rules authorizes principal, admin, office_admin, office_staff, class_teacher, while domain types define only three roles. Class teachers can access student paths without class/student assignment. No file path was exercised.

App was in Sample Data mode. No emulator/CLI/firebase.json was present. Rules were static-reviewed only. No Firebase query/rules/Storage runtime test, cloud access, edit, or deployment was done.
